# Changelog

Releases are tagged `v<version>`; each entry says what changed for an operator.

## 0.9.0

Review round 5 (the fourth review's B1-B3):

- **The posting refusal is structural.** With `post.accounts` set, posting is off unless every `guard.allowTools` and `guard.operatorTools` entry can only match verifiably read-only tools: on the built-in read-only list, or listed with `readOnlyHint: true` (the gateway caches trusted servers' hints in `state/mcp-readonly.json` at session start; no cache means fail closed). Entries matching a made-up future name (`overseer/coordinator_brand_new_tool`, `.*`, `^overseer/coordinator_.*`) are refused, and the dangerous verbs (`send`, `relay`, `message`, `job_add`, `job_dispatch`, `job_approve`, `schedule_add`, `open`, `close`, `decide`, `job_note`, `job_wake`, `job_redrive`, `job_reroute`, `job_switch`, `job_correct`) are checked under both `coordinator_` and `overseer_`. `operatorTools` is included.
- **Work module.** Posting is off when `work.command` is set and a group has a `work` project, because `work_queue` runs unasked and Carl cannot tell whether the job is sandboxed. `"work": {"command": [...], "sandboxed": true}` is the operator's statement that it is.
- **Notice failure removes the slot.** The agent-slot notice is sent straight to Telegram, not queued, so a failed send throws and the slot is removed.
- **Unattended reads.** The built-in read-only list now matches the real `coordinator_` tool names (and keeps `overseer_`), so unattended runs are no longer refused `coordinator_job_list` and similar.
- **Cards.** Long cards are sent one at a time with the card id on every piece; a permanent Telegram refusal (blocked bot, chat gone) stops the retries and says so once; the clear-pending card no longer promises a re-click; the message for a ledger/draft mismatch names how to recover.
- **Docs.** `docs/POSTING.md` states the rule as it is, names the real tools, says the descriptor check is the gateway's, drops the unsupported browser claim and the duplicate agent paragraph, and corrects "waits out" and "nothing is stranded".

Review round 4 (the third review's F1-F6 and Lows):

- **Posting is off while an unsandboxed tool is auto-allowed.** With `post.accounts` set, config load refuses to enable posting while any `guard.allowTools` entry auto-allows `overseer_send`, `overseer_message`, `overseer_job_add`, `overseer_open`, `overseer_close`, `overseer_job_dispatch`, `overseer_job_approve` or `overseer_schedule_add` (explicit list in `src/post/safety.ts`). The reason is delivered to the home chat, `carl post status` leads with it, and nothing posts. To turn posting on, remove those entries from `guard.allowTools` in `carl.json` (the tools then ask) and restart. The approval key stays a 0600 file readable by an unsandboxed process of the same user (a Keychain item made by `security` is equally readable); docs say so.
- **No wedged draft.** A failed write-ahead appends `cleared` to the ledger; one effective view of draft plus ledger is used by post, cards, approve, status and schedule (so `clear-pending` and `record-live` work from the ledger alone); a live dry run takes the draft's lock; the ledger's hashes are checked against the current text; a repost of identical text from the same path is refused; an unreadable ledger stops posting.
- **Pre-click check.** It waits for the exact text and refuses (retryable) when the profile timeline did not draw; only X's empty-profile state lets a click go on no posts.
- **Cards.** Not collapsed, show who asked, long cards sent in several messages, an agent's denied card is not asked again for six hours, a card that failed to send is retried after a minute, callback ids use random bytes and a press must come from the card's message. Approve is bound to the hash the card was described with; the approval also covers the draft's path.
- **Smaller.** The agent cannot remove or pause a post job; a slot whose operator notice fails is not kept; posting refuses once the relay descriptor differs from start; the default descriptor is closed even when `OVERSEER_*` names another; `post-approval.key` is denied by name in any Carl's profile and loopback port 9222 is closed; doc claims about guarantees softened.

Review rounds 2 and 3 changed these (the entries below describe 0.9.0 as it now behaves):

- **Approval is decided on your channel, not at a terminal.** `carl post approve`, `clear-pending` and `record-live <draft> <url>` (new) only create a card in `CARL_HOME/state/post-cards/`; the running gateway shows it in the Telegram home chat with the exact parts, account, profile URL and text hash, and the action happens only when a user in `telegram.allowFrom` presses Allow, bound to the keyed hash of what was shown. The agent's tool gains `request_approval` (it can ask, never answer). The TTY check is removed. `overseer_send` / `overseer_job_add` in `allowTools` can no longer approve; a program running outside the sandbox can still read the key.
- **Approval hash.** `approved_hash` is purpose-separated from `dry_run_hash` and covers the `approved` stamp, so a dry run's hash is not an approval and a stamp cannot be edited or copied.
- **Browser sandbox.** Besides `~/Library/Application Support/OverSeer/browser`, the profile denies `~/.config/overseer-browser`, the `runtime_root` of `active-connection.json` (or `$OVERSEER_BROWSER_CONNECTION`) and `$OVERSEER_BROWSER_RUNTIME`, and refuses any unix socket named `overseer-browser*.sock`; a macOS test connects under the real profile.
- **Crash safety.** The write-ahead record also holds the profile's newest status id (a rerun no longer depends on clocks; two minutes of clock slack on the approval bound), is written to a fsynced ledger (`state/post-ledger.jsonl`) as well as the draft (draft writes are fsynced), and a stale save of the draft cannot erase it. A part whose exact text is already on the profile is refused before the click. Bare domains (`example.org/x`) are refused at render. Pending parts cannot be re-approved.
- **Scheduling.** The agent's slot must be at least 15 minutes away and the operator is messaged; a post job run before its slot without force is a no-op that changes no state (UltraTerm's Run button no longer burns attempts); a re-approval ends `--skip-dry-run`; adopted jobs are tracked, so a CLI removal is not undone; a lock is taken over only when its owner is dead.
- **Gateway start.** A session command that does not resolve is logged, messaged to the home chat and flagged first in `carl post status`; `~` and absolute `session.command` work. A profile link that never draws is retryable, not "wrong account".
- Also refused: U+2028/2029, soft hyphen, zero-width space/non-joiner, U+2060-2064, BOM and tag characters in drafts; a thread's `first_reply`, `## First reply`, `text` and `## Post` (would be dropped silently).

- **Post primitive.** `carl post dry-run | approve | now | schedule | clear-pending | record-live | status` publishes a post from a Markdown draft (front matter: `platform`, `account`, `text` or `thread`, optional `reply`). One adapter contract per platform (`src/post/types.ts`, registry in `src/post/registry.ts`); X is the first adapter, driven through an owned `overseer-browser` session with an explicit `--timeout`.
- **No double click.** A `pending_part` record is written (and must succeed) before every Post click. Any failure after the click is final and never retried; a rerun only looks for the pending part on the profile and refuses until the operator records it (`record-live`) or clears it (`clear-pending`), each by answering a card. Only failures before a click are retried by the scheduler.
- **Verification.** A live post counts only if its whole normalised text matches (emoji read from `<img alt>`), X created it no earlier than the approval, its id is newer than the profile's newest post before the click and than the previous part, and it is not already recorded. Recorded parent URLs must be `/<handle>/status/<id>` of the account, once each. The browser must be signed in to the configured account (checked before filling), the profile must be an https X URL, and the composer is re-read at click time.
- **Approval gate.** Posting, live or scheduled, refuses unless the draft carries `approved:` and an `approved_hash` that is an HMAC-SHA256 (key `CARL_HOME/post-approval.key`, 0600, denied to the sandbox) over platform, account, profile, text, thread and reply. The approval card shows what is live, is bound to the hash of what it displayed (a draft edited while it was open is refused), and an edited live part cannot be re-approved. Control and bidi characters in a draft are refused. A live dry run of the exact text (`dry_run_hash`) is required unless the operator passes `--skip-dry-run`.
- **Agent boundary.** The `post_draft` tool drafts, dry-runs and gives an approved draft its first slot; it cannot approve, post at once, change a slot or choose `late`, and the `schedule` tool refuses to run or resume a post job. A post job does nothing when run before its slot unless the operator forces it. With `post.accounts` configured, the sandbox profile denies the browser control folders (read, write, socket) and the approval key, and the guard refuses `overseer-browser` in the agent's shell. A `draftsDir` (or draft) inside a folder the agent can write is refused.
- **Durable scheduling.** A new `post` schedule job kind (one-time, in `schedules.json`) fires a draft at `scheduled_at`. A slot missed by more than `post.missedWindowMinutes` (default 180) is skipped and the delivered message says so (never when a click was started); `--late post` (operator only) posts it late. `schedules.json` writes are locked and merged: the CLI no longer rewrites running job state, and a job it removes is dropped by a running gateway.
- **Gateway PATH.** `post.accounts.*.session.command` is resolved from the operator's PATH at start and pinned like Carl's other programs, so scheduled posts can start the browser CLI from the gateway. Child processes get a scrubbed environment.
- **Config.** `post` in `carl.json`: `draftsDir`, `missedWindowMinutes`, `retex`, and `accounts` (the only place accounts are defined).
- Draft writes are compare-and-set against the file as read (`retex set --if-hash` when retex is installed and nothing is cleared, otherwise an atomic write); a failing retex is an error. A fully live draft that was never marked Posted is just marked Posted. `media:` and a thread's `reply` are refused; inline `[..]` lists apply only to `thread`, `thread_urls`, `media`; X length counts CJK and emoji as 2.
- Docs: `docs/POSTING.md` and a README section.
